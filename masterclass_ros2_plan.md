# Мастер-класс по ROS2 на MEPhI_ROS2_drone

**Аудитория:** 8 человек, 11 класс и младше, опыт смешанный (часть без опыта программирования/терминала, часть — с Python в школе)
**Длительность:** ядро программы — 60 минут, с буфером до 90 минут
**Оборудование:** 8 × Windows ПК с ВМ (ROS2 Humble), 1 робот (гусеничная платформа, Wi-Fi «A_220»)

## Цель

Каждый ученик:
1. Своими руками подвигает что-то через ROS2 (сначала в симуляторе, потом — по-настоящему).
2. Увидит на своём экране живые данные с настоящего робота.
3. Лично порулит настоящим роботом и проведёт его через полосу препятствий.

Основная ставка — на код и на «пощупать топики руками». Лидар работает нестабильно, если провёл долго без переподключения, но стабильно и предсказуемо сразу после свежего переподключения USB (см. «Известные ограничения»), поэтому он включён как отдельный блок, а не в ядро программы — на случай, если в моменте не заведётся.

**Важное архитектурное решение (проверено на практике):** нативная ROS2-сеть (когда ВМ ученика напрямую видит топики робота по Wi-Fi через `ROS_DOMAIN_ID`) оказалась ненадёжной — discovery (`ros2 topic list`) работает, а вот реальные данные по UDP от ВМ к роботу иногда не проходят (подтверждено даже сырым UDP-тестом в обход ROS2). Причина — в поведении конкретной Wi-Fi сети, а не в коде. Поэтому Блоки 2, 3 и бонус используют **SSH напрямую на робота** вместо нативной сети: ученик подключается по SSH (это самый надёжный протокол на любой институциональной сети — работает даже там, где произвольный UDP режется) и запускает команды прямо на роботе. Всё выполняется локально на Pi, по сети едут только нажатия клавиш (и для RViz — картинка через X11), а не сырой ROS2-трафик. Это ещё и проще для ученика: не нужно настраивать ROS2 у себя, только SSH.

## Подготовка заранее (не в день мастер-класса)

- [ ] На всех студенческих ВМ нужен только: `ros-humble-desktop` (или минимум `ros-humble-turtlesim`) для Блока 1, и SSH-клиент (в Linux-ВМ уже встроен). Для Блоков 2/3 и бонуса ROS2 на самой ВМ не требуется вообще — все команды выполняются на роботе через SSH.
- [ ] На роботе прописан `ROS_DOMAIN_ID=42` (уже сделано, в `~/.bashrc` и во всех целях `Makefile`) — это нужно только для самого робота, студенческие ВМ теперь этого не касается.
- [ ] Узнать и записать текущий IP робота на классной сети «A_220» (`hostname -I` на самом роботе) — вывести на доске/экране, чтобы ученики подставляли его в команду `ssh`. IP на A_220 будет отличаться от того, что использовался при подготовке.
- [ ] **Проверить заранее (не в день Х):** SSH до робота реально работает с обычного ученического ПК по Wi-Fi «A_220» — это гораздо надёжнее, чем нативная ROS2-сеть (см. ниже почему), но всё равно стоит один раз проверить `ssh pi@<IP>` с тестовой машины на A_220.
- [ ] Убедиться, что пароль пользователя `pi` на роботе — что-то осмысленное (не словарное), и что все ученики его знают/видят на доске — аккаунт общий на всех, это нормально для мастер-класса, но не должно быть первым паролём, который подберёт скрипт.
- [ ] Зарядить робота, проверить, что мотор-плата подключена (`ls -l /dev/ttyUSB_MOTOR` на роботе должен существовать).
- [ ] **Лидар**: контакт USB дребезжит при долгой работе без переподключения (окно стабильности — где-то между 2 и 11 минутами, дальше `/scan` может замолкнуть без единой ошибки в логе). Решение — `make lidar-watchdog` (нужен `sudo`, пароль спросит один раз при старте): сам следит за `/scan`, при обрыве программно "передёргивает" USB-порт (без физического доступа) и перезапускает ноду, пишет всё в `/tmp/lidar_watchdog.log`. Запускать в отдельном терминале, параллельно с bringup.
- [ ] На роботе заранее подняты: `make bringup INCLUDE_RPLIDAR=False` (мотор+описание) в одном терминале + `make lidar-watchdog` (лидар отдельно, с автовосстановлением) в другом — пусть работают весь мастер-класс, чтобы не тратить время при учениках.
- [ ] Полоса препятствий: 4-6 кубиков/конусов, размеченный старт и финиш, минимум 1.5×1.5 м свободного пространства.
- [ ] Распечатать/вывести на экран список команд ниже (раздел «Шпаргалка команд»).
- [ ] Заранее решить, где стоит «место водителя» (один ноутбук/место у робота, к которому по очереди подходят ученики) — так безопаснее и быстрее, чем гонять teleop с 8 разных машин одновременно.

## Вступление (5 мин)

**Сказать:**
- «ROS2 — это не язык программирования, а способ, которым разные программы одного робота разговаривают друг с другом. Сегодня робот будет состоять из нескольких независимых программ — они называются *нодами* (node, "узел"). Одна нода читает лидар, другая крутит моторы, третья решает, куда ехать. Они не знают друг о друге напрямую — они пишут сообщения в общие "каналы", которые называются *топики* (topic). Кто-то пишет в топик, кто-то читает — как канал в мессенджере».
- «Сегодня каждый лично покрутит виртуальную черепашку, а потом — настоящего гусеничного робота».

**Техника безопасности (обязательно проговорить):**
- Во время движения робота руками колёс/гусениц не касаться.
- К роботу подходит только тот, чья очередь, остальные — на расстоянии.
- Полоса препятствий — не более одной попытки без объявления «еду» вслух.

## Блок 1 — Разминка в симуляторе, 15 мин (все параллельно, каждый на своей ВМ)

Цель: без риска, без сети, без робота — прямо на своей ВМ понять, что такое нода и топик, и лично подвигать что-то через ROS2.

**Шпаргалка команд (два терминала):**
```bash
source /opt/ros/humble/setup.bash

# Терминал 1: запустить черепашку
ros2 run turtlesim turtlesim_node

# Терминал 2: порулить ей с клавиатуры (стрелки)
ros2 run turtlesim turtle_teleop_key
```

**Что объяснять по ходу:**
- «`ros2 run <пакет> <нода>` запускает одну программу-ноду».
- Пока едет черепашка — в третьем терминале показать:
  ```bash
  ros2 node list
  ros2 topic list
  ros2 topic echo /turtle1/cmd_vel
  ```
  «Видите — как только жмёте стрелку, здесь появляется сообщение. Это и есть топик `/cmd_vel` — команда скорости. Teleop её пишет, черепашка читает».
- Для тех, кто быстрее справился (опциональное усложнение для учеников с опытом): дать команду вручную, без клавиатуры:
  ```bash
  ros2 topic pub /turtle1/cmd_vel geometry_msgs/msg/Twist "{linear: {x: 2.0}, angular: {z: 1.0}}" --once
  ```
  «Мы только что напрямую написали в топик, без всякого teleop — черепашка не знает разницы».

## Блок 2 — Подключаемся к настоящему роботу, 15 мин (все параллельно)

Цель: у каждого на экране — живые данные с настоящего, физического робота, стоящего в кабинете. Пока без управления — только смотрим (это безопасно и не требует очереди).

Подключаемся по SSH прямо на робота и смотрим его топики оттуда же — вместо того чтобы пытаться увидеть их по сети со своей ВМ (это оказалось ненадёжно, см. вступление).

**Шпаргалка команд:**
```bash
ssh pi@<IP_РОБОТА>
# ввести пароль

source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=42

ros2 topic list          # должны появиться темы робота: /cmd_vel, /joint_states, /tf...
ros2 topic hz /joint_states   # ~50 Гц — робот "жив" и постоянно докладывает о себе
ros2 topic echo /joint_states --once
```

**Что объяснять:**
- «Мы только что зашли по SSH прямо в компьютер робота — это как удалённый рабочий стол, только текстовый. Дальше все команды выполняются НА роботе, а не у вас на экране — но результат вы видите здесь же, в терминале».
- «Робот сейчас реально стоит вот тут (показать), включён и работает — и мы это видим не по рассказам, а по живым данным, которые он публикует прямо сейчас».
- «`ROS_DOMAIN_ID` — это как номер радиоканала, на котором ноды одного робота разговаривают друг с другом. Мы задаём его, чтобы наша SSH-сессия могла слушать эти топики».
- Если `ros2 topic list` пустой — проверить, что команда `export ROS_DOMAIN_ID=42` действительно была введена в ЭТОЙ SSH-сессии (при новом подключении надо вводить заново).

**Если осталось время у сильных учеников:** показать `rqt_graph` (если установлен) — визуальная схема нод и топиков, «карта» того, что происходит внутри робота.

## Блок 3 — Очередь за руль, до 25-40 мин (по одному, остальные заняты своим)

Это главный практический результат мастер-класса — каждый лично провёл настоящего робота через препятствия.

**Организация:** очередь за руль теперь можно вести с любого ученического ПК по очереди (не обязательно одно специальное «место водителя») — каждый заходит по SSH со своей машины. Пока не их очередь — продолжают исследовать топики/черепашку у себя (не простаивают).

**Команда для водителя (со своего ПК):**
```bash
ssh pi@<IP_РОБОТА>
# ввести пароль

source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=42
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```
Управление: `i` — вперёд, `,` — назад, `j`/`l` — разворот на месте, `k` — стоп. **Важно: только одна SSH-сессия с teleop должна быть открыта одновременно** (аккаунт на роботе общий, команды с разных сессий будут конфликтовать) — предыдущий ученик обязательно жмёт `k`, потом `Ctrl+C`, потом `exit` из SSH, только после этого следующий заходит.

**Задание:** доехать от точки А до точки Б, не задев препятствия. Как срулил — уступает место.

**Что объяснять, пока едет:**
- «Каждое нажатие клавиши — это то же самое сообщение в топик `/cmd_vel`, которое вы видели у черепашки пять минут назад. Разницы для ROS2 нет — что виртуальная черепашка, что настоящий робот с гусеницами: программе всё равно, что в реальности».

## Бонус — лидар и RViz, 10 мин (если осталось время)

Стоит того, чтобы сделать: за пару минут непрерывной проверки лидар держится стабильно после свежего переподключения (см. подготовку). Но если именно в моменте не завёлся — не тратить время на починку при учениках, просто пропустить блок, ядро программы (блоки 1-3) от этого не страдает.

RViz тоже запускается прямо на роботе через SSH, но с флагом `-X` (X11-форвардинг) — окно RViz реально рисуется на Pi, а картинка передаётся по SSH и открывается у вас на экране. Проверено на практике, работает без нативной ROS2-сети:
```bash
ssh -X pi@<IP_РОБОТА>
# ввести пароль

source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=42
rviz2
```
В открывшемся окне: Add → By topic → `/scan` → LaserScan → Add, затем Fixed Frame = `base_link`.

Показать на проекторе (или по очереди на своих экранах через ту же SSH-команду), как робот "видит" комнату лучом лидара в реальном времени. Провезти его — все видят, как обновляется скан.

**Важно:** флаг `-X` обязателен именно для этой команды (без него окно не откроется) — в отличие от Блоков 2 и 3, где `-X` не нужен (там нет графики).

## Шпаргалка на случай неполадок

| Симптом | Что проверить |
|---|---|
| `ssh pi@<IP>` не подключается вообще | Верный ли IP (мог поменяться на A_220 — смотреть заново `hostname -I` на роботе); та же ли Wi-Fi сеть у ученика |
| SSH подключился, но `ros2 topic list` пустой | Забыли `export ROS_DOMAIN_ID=42` в текущей SSH-сессии — при новом подключении вводить заново |
| Робот не реагирует на teleop | Не открыта ли **вторая** SSH-сессия с teleop где-то ещё (конфликт команд, аккаунт общий); жив ли bringup на роботе (`pgrep -af ros2_control_node` на Pi) |
| Едет не в ту сторону / не крутится нужная гусеница | Уже почищено на момент подготовки — если повторилось, перезапустить `make bringup` на роботе |
| RViz (`rviz2` через `ssh -X`) не открывает окно | Проверить, что подключались именно с флагом `-X` (не просто `ssh`); попробовать переподключиться |
| Совсем нет связи с роботом по Wi-Fi | Проверить, что сам SSH-порт (22) не заблокирован на A_220 — это редкость, но если так, брать резервный роутер |

## Известные ограничения на момент подготовки

- **RPLIDAR нестабилен, если долго не переподключался**: за долгую тестовую сессию (много попыток запуска подряд без физического переподключения USB) лидар постепенно перестаёт проходить рукопожатие — каждый раз отказ в разном месте протокола (то таймаут на старте, то падает на health-check, то на старте скана), что указывает на плавающий контакт/наводки, а не на программную проблему (порт и baud rate верны). **Чинится физическим переподключением USB-кабеля** — после этого проверено: рукопожатие проходит с первого раза, `/scan` публикуется стабильно (проверено больше 2 минут непрерывной работы, ни одной ошибки). Насколько велико "окно стабильности" при долгой работе без переподключения (весь ли 90-минутный мастер-класс продержится) — не проверено, поэтому в подготовке заложено переподключение прямо перед стартом и готовность повторить это в середине занятия при необходимости.
- **Правая гусеница медленнее левой при развороте на месте** (примерно в 2.5-3 раза, иногда кратковременно останавливается совсем) — подтверждено, что не баг в коде (энкодеры/PID симметричны в софте), похоже на механику (натяжение гусеницы) или шумный энкодер справа. Не мешает прямолинейному движению и полосе препятствий, если её не завязывать на точный разворот на месте.
- **Нативная ROS2-сеть между студенческой ВМ и роботом ненадёжна на текущей Wi-Fi сети (18KPU)**: discovery работает (`ros2 topic list` видит топики робота), но реальные данные по UDP от ВМ к роботу иногда не доходят — подтверждено сырым UDP-тестом в обход ROS2/DDS полностью (голый `nc -u` пакет от ноутбука до робота не долетал, в обратную сторону — долетал). Проверили и исключили: домен, файрвол (ufw неактивен), Docker/VPN-интерфейсы, файл конфигурации DDS. Похоже на особенность самой сети (не исключена изоляция клиентов или асимметричная фильтрация трафика), а не на локальную настройку конкретной машины. **Решение — полностью обошли проблему через SSH** (см. Блоки 2/3/бонус): SSH (TCP) работал безотказно на протяжении всей диагностики, поэтому все команды теперь выполняются прямо на роботе через SSH-сессию, а не по нативной ROS2-сети с ВМ ученика. Не проверено, ведёт ли себя так же сеть A_220 (тестировали на 18KPU) — но раз план теперь не зависит от нативной сети вообще, это не критично.
