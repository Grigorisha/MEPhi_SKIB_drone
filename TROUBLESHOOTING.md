## 1. Внешняя машина не видит робота (firewall)

**Статус: исправлено для текущей сети 10.1.18.0/24. В новой сети вернётся — см. блок про смену сети.**

**Это самая коварная неисправность из всех — на неё ушло больше всего времени.**

### Симптом

С ноутбука в той же сети:

```bash
ros2 node list      # пусто
ros2 topic list     # только /parameter_events и /rosout — свои, локальные
ping 10.1.18.175    # идёт нормально
ssh Vindicator2     # работает
```

При этом на самом роботе всё прекрасно: `ros2 node list` показывает все пять нод, `/scan` публикуется, контроллеры `active`.

**Ошибок не появляется нигде.** Ни в логах робота, ни на ноутбуке. Просто пустота — и именно поэтому легко уйти искать причину не там: в `ROS_DOMAIN_ID`, в версиях ROS, в настройках Wi-Fi.

### Причина

На Pi включён **ufw** (`active`, `enabled`). Он пропускает SSH, потому что порт 22 разрешён явно, и отбрасывает весь остальной входящий трафик — включая DDS.

### Как отличить от других сетевых проблем

Признак, который сразу указывает на firewall — **асимметрия UDP** при живом ping в обе стороны:

```bash
# На роботе — слушаем:
python3 -c "
import socket
s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM); s.bind(('0.0.0.0',7412)); s.settimeout(12)
try: print('ПРИНЯТО:', s.recvfrom(1024))
except Exception as e: print('НЕ ПРИНЯТО:', type(e).__name__)"

# На ноутбуке — шлём:
python3 -c "
import socket
socket.socket(socket.AF_INET,socket.SOCK_DGRAM).sendto(b'test',('10.1.18.175',7412))"
```

Если пакеты **от робота** доходят, а **к роботу** — нет, это firewall на приёмной стороне. Ни точка доступа, ни DDS так себя не ведут.

### Лечение

```bash
make net-allow        # определит подсеть сам и поставит правило
```

или вручную:

```bash
sudo ufw allow from 10.1.18.0/24 proto udp
sudo ufw reload
```

**Почему разрешается весь UDP, а не список портов.** Фиксированы только discovery-порты (для домена 42 это `7400 + 250×42 = 17900`). Весь остальной обмен FastDDS ведёт по **динамическим** портам, которые меняются при каждом перезапуске нод — правило по номерам портов будет работать до первого рестарта.

### ⚠️ Если сеть будет другой (выставка, другой роутер)

**Правило ufw привязано к подсети. В новой сети оно перестанет подходить, и симптом вернётся полностью — включая обманчиво живой ping.** Это первое, что нужно проверять на новой площадке.

Порядок действий на новом месте:

```bash
# 1. Посмотреть, что вообще происходит с сетью — sudo не нужен
make net-check

# 2. Открыть DDS для новой подсети (определится автоматически)
make net-allow

# 3. Прибраться: убрать правила от прежних сетей
bash mephi_hw_tests/ros2_net_setup.sh clean
```

`net-check` покажет интерфейс, SSID, IP, подсеть, состояние ufw и слушает ли DDS — этого достаточно, чтобы понять, где встало.

**Чек-лист для новой сети:**

- [ ] `ROS_DOMAIN_ID` одинаков на роботе и ноутбуке (у нас везде **42**)
- [ ] ufw открыт для **новой** подсети — `make net-allow`
- [ ] Старые правила убраны, чтобы не копились
- [ ] На ноутбуке `ros2 node list` показывает ноды робота
- [ ] Статический IP в `~/setup_network.sh` прописан под **старую** сеть `18KPU` (`10.1.18.175`). В другой сети Pi может не подняться вообще — проверьте до выезда

**Если ноды не появились даже после открытия ufw**, причина в multicast: многие точки доступа его режут (изоляция клиентов). Проверка:

```bash
# на роботе
ros2 multicast receive
# на ноутбуке
ros2 multicast send
```

Не дошло — переводите discovery на unicast. Создайте на **обеих** машинах файл `fastdds_peers.xml`:

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<dds xmlns="http://www.eprosima.com">
  <profiles>
    <participant profile_name="unicast" is_default_profile="true">
      <rtps>
        <builtin>
          <initialPeersList>
            <!-- Здесь адреса ВСЕХ машин: и робота, и ноутбуков -->
            <locator><udpv4><address>10.1.18.175</address></udpv4></locator>
            <locator><udpv4><address>10.1.18.69</address></udpv4></locator>
          </initialPeersList>
        </builtin>
      </rtps>
    </participant>
  </profiles>
</dds>
```

и подключите его перед запуском нод:

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=/полный/путь/fastdds_peers.xml
```

Адреса внутри файла придётся поправить под новую сеть — в этом и смысл: unicast не зависит от того, пропускает ли точка доступа multicast.

**Самый надёжный вариант для выставки — привезти свой роутер.** Тогда подсеть известна заранее, правило ufw ставится один раз, а поведение чужой точки доступа перестаёт вас касаться.

## 2. rviz ничего не показывает

**Симптом.** rviz2 запускается, но окно пустое. В левой панели красным: `Fixed Frame [map] does not exist`. Данные при этом идут — `ros2 topic hz /scan` подтверждает.

**Причина.** В `andino_bringup/rviz/andino.rviz` полем `Fixed Frame` был задан `map`. Этот фрейм публикуется **только при запущенном SLAM**. Без него у rviz нет системы координат, и он не рисует ни облако точек, ни модель робота.

Дерево TF без SLAM начинается с `odom`:

```
odom → base_link → second_base_link → rplidar_laser_link
```

**Лечение.** Исправлено коммитом `3bd50ee`: `Fixed Frame` переведён на `odom`, который публикует `diff_controller` всегда. У SLAM и Nav2 свои rviz-конфиги, их правка не затронула.

Если увидите это снова — переключите Fixed Frame на `odom` прямо в rviz (Global Options сверху слева) либо запустите SLAM.

## 3. В rviz нет модели робота

**Симптом.** Облако точек видно, робота нет. В логе десятки строк `Error retrieving file [package://andino_description/meshes/...]: Package [andino_description] does not exist`.

**Причина.** rviz на внешней машине получает URDF по теме `/robot_description`, но STL-меши в нём указаны как `package://` — их нужно взять с диска, а пакета на ноутбуке нет.

**Лечение.** Скопировать пакет на внешнюю машину и указать путь:

```bash
scp -r Vindicator2:/home/pi/MEPhi_SKIB_drone/MEPhI_ROS2_drone/install/andino_description ~/куда-нибудь/
export AMENT_PREFIX_PATH=~/куда-нибудь/andino_description:$AMENT_PREFIX_PATH
```

На ноутбуке это уже сделано: `~/Documents/vindicator/rviz.sh` поднимает rviz со всем необходимым.

## 4. Лидар отваливается по USB

**Симптом.** `/scan` перестаёт публиковаться. Нода `rplidar_composition` при этом **жива**, в логе ни одной ошибки.

**Причина.** Дребезг USB-контакта. Подтверждено практикой: помогает физическое передёргивание кабеля.

**Текущее лечение — костыль, но рабочий.** `mephi-lidar-watchdog.service` раз в 10 секунд проверяет `/scan`, при пропаже данных делает программный `usbreset` и перезапускает ноду. Восстановление занимает около 10 секунд.

Статистика на 22.08: **3 срабатывания**, последнее — при загрузке. После этого 2 ч 35 мин без сбоев.

**Что осталось.** Лечить причину: зафиксировать разъём механически, заменить кабель на короткий экранированный, проверить просадку питания. Watchdog оставить страховкой.

Лог: `/tmp/lidar_watchdog.log`

## 5. Радиус колеса расходится

**Не исправлено — нужен замер.**

Два файла задают радиус по-разному:

| Файл | Значение | На что влияет |
|---|---|---|
| `andino_description/config/andino/wheel.yaml` | `0.045` | модель в rviz |
| `andino_control/config/andino_controllers.yaml` | `0.035` | **одометрия** |

В контроллер загружено `0.035` (проверено через `ros2 param get /diff_controller wheel_radius`).

Разница **29 %**. Одометрия систематически врёт, карта SLAM плывёт, Nav2 промахивается.

**Что сделать.** Замерить колесо штангенциркулем, привести оба файла к реальному значению, пересобрать. Проверка — проехать размеченные 2 м и сверить с `/odom`.

Заодно не подтверждено `enc_ticks_per_rev: 585` — проверяется поворотом колеса ровно на один оборот со сверкой счётчика.

## 6. Нет часов реального времени

**Статус: частично исправлено — fake-hwclock стоит, RTC-модуля нет.**

`timedatectl` сообщает `RTC time: n/a`. При аптайме в 1 час система рапортовала о загрузке 26 августа 2025 — фиктивное время держалось, пока NTP не подтянул настоящее.

**Чем опасно.** Без интернета время останется неверным. Тогда TF-таймстампы уезжают, Nav2 отбрасывает «просроченные» данные, rviz показывает пустоту. Выглядит как полный отказ робота без единой ошибки в логе — то есть очень похоже на §1, и легко пойти искать не там.

**Лечение.** Модуль `DS3231` на I2C — полноценное решение, пока не поставлен.

**Сделано 22.08:** установлен `fake-hwclock` (enabled). Он сохраняет время при выключении
и восстанавливает при загрузке, так что откат на год назад больше не грозит. Точность он не
даёт — при длительном простое без сети часы всё равно отстанут, но скачок будет измеряться
часами, а не месяцами, и TF от этого уже не разваливается.

## 8. Мультиплексор команд (twist_mux)

**Статус: работает с 22.08.** Проверено: нода видна в `ros2 node list`, темы
`cmd_vel_joy` / `cmd_vel_keyboard` / `cmd_vel_nav` созданы, приоритеты 30/20/10
загружены, `/cmd_vel` имеет ровно одного публикатора (`twist_mux`) и одного
подписчика (`diff_controller`).

**Зачем нужен.** Без мультиплексора джойстик, клавиатура и Nav2 пишут в `/cmd_vel`
одновременно и перебивают друг друга. У оператора нет способа перехватить управление,
если робот поехал на посетителя. Ради этого приоритеты и задумывались.

### Как настроено

Пакет `ros-humble-twist-mux 4.3.0` установлен, нода поднимается в bringup,
источники разведены по темам:

```
джойстик   -> /cmd_vel_joy       приоритет 30   человек всегда главнее
клавиатура -> /cmd_vel_keyboard  приоритет 20
навигация  -> /cmd_vel_nav       приоритет 10   Nav2 уступает человеку
                                    |
                            twist_mux -> /cmd_vel -> diff_controller
```

Контроллер намеренно оставлен на `/cmd_vel` — менять его ремапы не потребовалось.
Навигация заведена на отдельную `cmd_vel_nav`: если оставить её на `/cmd_vel`, у
мультиплексора получится петля вход-выход.

Файлы: `andino_bringup/config/twist_mux.yaml`, `andino_bringup/launch/andino_robot.launch.py`,
`teleop_keyboard.launch.py`, `teleop_joystick.launch.py`.

### Если нода не стартует: устаревший diagnostic-updater

Так было 22.08 до обновления пакета. Симптом вернётся, если систему переустановят
или откатят пакеты — нода стартует и сразу умирает с кодом 127:

```
twist_mux: error while loading shared libraries: libdiagnostic_updater.so:
cannot open shared object file: No such file or directory
```

Причина неочевидная. Пакет `ros-humble-diagnostic-updater` **установлен**, но версии
**4.0.6** — а в ней лежит только Python-часть, C++ библиотеки `libdiagnostic_updater.so`
в пакете нет вовсе. Свежий `twist_mux 4.3.0` собран против версии **4.0.7**, где она
появилась. В deb зависимость указана без номера версии, поэтому apt считает уже
установленный пакет подходящим и не обновляет его.

**Лечение** (обновление затрагивает ровно один пакет, ничего лишнего не тянет):

```bash
sudo apt install -y ros-humble-diagnostic-updater
sudo systemctl restart mephi-bringup
```

**Проверка, что заработало** — именно так, а не через `pgrep`:

```bash
ros2 node list | grep twist_mux        # нода должна быть в списке
ros2 topic list | grep cmd_vel         # должны появиться cmd_vel_joy/keyboard/nav
```

> `pgrep -f twist_mux` для проверки **не годится**: строка команды с самим словом
> `twist_mux` попадает в результат, и проверка радостно рапортует об успехе, пока
> нода в это время падает в цикле. На этом уже один раз обожглись.

**Важно при настройке Nav2:** его выход нужно ремапить на `/cmd_vel_nav`. Если Nav2
оставить публикующим прямо в `/cmd_vel`, он будет писать в обход мультиплексора, и
джойстик перестанет иметь приоритет — пропадёт ровно то, ради чего всё делалось.

## 9. Таймауты связи с Arduino

**Найдено 22.08, не разобрано.**

**Симптом.** В журнале `mephi-bringup` регулярно появляется:

```
[ros2_control_node] Response to m 0 0 timed out.
[ros2_control_node] Response to e timed out.
```

Топики при этом живут, `/odom` держит стабильные 50 Гц, контроллеры `active` — по внешним
признакам всё исправно. Увидеть можно только в журнале.

**Масштаб.** 30 случаев за пять часов работы, распределены равномерно — примерно раз в
полчаса, пачками по 1–3 подряд. Таймаутят две команды:

| Команда | Что делает | Случаев |
|---|---|---|
| `m 0 0` | задать скорость моторам | 16 |
| `e` | прочитать счётчики энкодеров | 13 |

**Чем грозит.** Пропуск `e` — скачок в одометрии: позиция «прыгает» на величину, накопленную
за пропущенный цикл. Пропуск `m` — потерянная команда скорости, на ходу это ощущается как
рывок. От полной потери связи спасает автостоп в прошивке: без команд дольше 3 секунд моторы
глушатся сами.

**Где искать причину.** Таймаут задан в `andino_description/config/andino/hardware.yaml`
(`timeout: 1000` мс). Кандидаты, от простого к сложному:

- загрузка CPU на Pi в момент опроса — посмотреть `top` во время движения;
- USB-мост CH340 и качество кабеля — та же болячка, что у лидара в §4;
- прошивка не успевает: PID крутится на 30 Гц, а `controller_manager` опрашивает на 50 Гц,
  стоит сверить, не конкурируют ли циклы;
- слишком строгий таймаут — но поднимать его стоит последним делом, это лечение симптома,
  а не причины.

**Проверка после починки.** Час работы без единой строки `timed out` в выводе
`journalctl -u mephi-bringup`.

## 10. Робот пропадает из сети: конфликт IP

**Найдено 10.10.2026, лечится `mephi_hw_tests/fix_ip_conflict.sh`.**

**Симптом.** Робот «отваливается» на десятки секунд: рвутся SSH и Remmina, ping с
ноутбука то идёт, то нет. На самом роботе при этом Wi-Fi подключён, NetworkManager молчит,
но сторож `wifi-reconnect` иногда не может допинговать шлюз.

**Причина.** Робот брал **статический** `10.1.18.175` (`~/setup_network.sh`), а этот адрес
лежит внутри DHCP-диапазона роутера 18KPU. Роутер выдал его ещё и другому устройству —
судя по трафику, телефону с MAC `c2:39:39:6b:94:48`. Пока оба в сети, роутер и ноутбук
шлют пакеты робота то ему, то телефону.

**Как проверить.** В журнале ядра робота ufw отбрасывает ответы, которых робот не
запрашивал: DNS от `85.143.112.2/3` (робот ими не пользуется), HTTPS от облаков Huawei
и Google:

```bash
sudo journalctl -k | grep "UFW BLOCK" | grep "DST=10.1.18.175" | grep -E "SPT=(53|443) "
```

Пока робот выключен, на его адрес отвечает чужой MAC: `ip neigh show 10.1.18.175`
на ноутбуке. MAC Wi-Fi робота — `d8:3a:dd:cb:41:f8`.

**Лечение.** Робот получает адрес по DHCP:

```bash
sudo bash mephi_hw_tests/fix_ip_conflict.sh     # на роботе; SSH оборвётся
make find                                       # на ноутбуке: найдёт робота по MAC
```

`make find` прописывает новый адрес в `~/.ssh/config` (`Host Vindicator2`, ключ хоста
привязан к имени через `HostKeyAlias`), в профиль Remmina и в пакет для rviz. Постоянный
адрес без конфликтов даёт резервирование на роутере по MAC `d8:3a:dd:cb:41:f8`.
`~/setup_network.sh` снова ставит статический адрес — не запускайте его.

## 11. Пульт не переподключается сам

**Найдено 10.10.2026. Причина — разные ключи сопряжения у пульта и робота.**

**Как должно быть (проверено по btmon).** Flydigi Apex 5 (режим ПК, выдаёт себя за
Xbox One S) сам вызывает робота, предъявляет ключ, включает шифрование и только потом
открывает HID-каналы (PSM 17 и 19). Выключили и включили пульт — `js0` через ~2 с.
Перезагрузили робота — пульт на связи на ~20-й секунде загрузки. Ничего ставить не нужно.

**Как ломается.** Пульт перевели в режим сопряжения (меню Connect → Re-pairing), сопрягли
или удалили в blueman — и ключи у пульта и робота разошлись. Тогда пульт стучится
каждые ~8 с **без шифрования**, ядро Linux отвечает `Connection refused - security block`
и рвёт связь с `Authentication Failure`. В журнале bluetoothd при этом пусто — видно
только в btmon:

```bash
sudo btmon | grep -E "security block|Authentication Failure"
```

Отказ ядра — известная история ([bluez#2380](https://github.com/bluez/bluez/issues/2380)):
Linux не ждёт шифрования для входящего HID-канала, Windows ждёт.

**Лечение.** Сопрячь заново: пульт в режим сопряжения (меню Connect → Re-pairing),
на роботе `bash mephi_hw_tests/pair_gamepad.sh`. Скрипт сам ставит «доверять» — blueman
этого не делает, и недоверенный пульт робот не пустит.

Не надо: жать Re-pairing без нужды; сопрягать и удалять пульт через blueman.

**Тупики, чтобы не повторять.** Служба `mephi-gamepad-keeper` (вызывать пульт с робота)
выключена: построена на неверной догадке «пульт сам не вызывает робота». Её вызовы
сталкивались с вызовами пульта — `HCI 0x0B ACL Connection Already Exists` и
`Operation already in progress` означают встречное подключение, а не сбой чипа.
На таких столкновениях bluetoothd 5.64 однажды упал (SEGV, 10.10.2026 17:28).
`btmgmt ssp off` (обход из bluez#2380) при живом ключе не нужен.

## 12. Робот перезагружается сам

**Найдено 10.10.2026, причина не установлена.**

За день 10.10.2026 — больше десятка перезагрузок, и до 17:55 ни одной через штатный `reboot`
(в `last -x` нет записей shutdown). Причину последнего сброса хранит регистр SoC:

```bash
sudo vcgencmd get_rsts      # 1000 — пропало питание; 1020 — штатный reboot
```

После внезапной перезагрузки в 17:52 было `1000`: питание Pi пропадало. Несколько сбросов
случились вскоре после того, как подключался пульт — возможно, гусеницы тянули ток и
просаживали питание Pi. Либо питание выключали руками — это надо исключить первым.
Журнал за последние минуты перед сбросом теряется: journald не успевает записать.

Чёрный ящик на время разбора (не переживает перезагрузку — запускать заново):
`nohup python3 mephi_hw_tests/powerlog.py &` — раз в секунду пишет в `~/power.log` с
`O_SYNC` пульс, отклонение стика, флаг низкого напряжения `rpi_volt` и пинг шлюза.
