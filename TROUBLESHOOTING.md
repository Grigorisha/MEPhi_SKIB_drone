# Неисправности Vindicator2 и как их лечить

Живой список проблем робота: что уже поймано, чем лечится, что осталось.
Собран 22.08.2026 прямыми замерами на роботе `pi@10.1.18.175`.

Дополняйте по мере находок — это рабочий документ, а не отчёт.

---

## Шпаргалка: симптом → причина

| Что видно | Почти наверняка это | Куда смотреть |
|---|---|---|

## 1. Внешняя машина не видит робота (firewall)

**Это самая коварная неисправность из всех — на неё ушло больше всего времени.**

### Симптом

С ноутбука в той же сети:

```bash
ros2 node list      # пусто
ros2 topic list     # только /parameter_events и /rosout — свои, локальные
ping 10.1.18.175    # идёт нормально
ssh Vindicator2     # работает
```

При этом на самом роботе всё прекрасно: `ros2 node list` показывает все пять нод, `/scan` публикуется, контроллеры `active`.

**Ошибок не появляется нигде.** Ни в логах робота, ни на ноутбуке. Просто пустота — и именно поэтому легко уйти искать причину не там: в `ROS_DOMAIN_ID`, в версиях ROS, в настройках Wi-Fi.

### Причина

На Pi включён **ufw** (`active`, `enabled`). Он пропускает SSH, потому что порт 22 разрешён явно, и отбрасывает весь остальной входящий трафик — включая DDS.

### Как отличить от других сетевых проблем

Признак, который сразу указывает на firewall — **асимметрия UDP** при живом ping в обе стороны:

```bash
# На роботе — слушаем:
python3 -c "
import socket
s=socket.socket(socket.AF_INET,socket.SOCK_DGRAM); s.bind(('0.0.0.0',7412)); s.settimeout(12)
try: print('ПРИНЯТО:', s.recvfrom(1024))
except Exception as e: print('НЕ ПРИНЯТО:', type(e).__name__)"

# На ноутбуке — шлём:
python3 -c "
import socket
socket.socket(socket.AF_INET,socket.SOCK_DGRAM).sendto(b'test',('10.1.18.175',7412))"
```

Если пакеты **от робота** доходят, а **к роботу** — нет, это firewall на приёмной стороне. Ни точка доступа, ни DDS так себя не ведут.

### Лечение

```bash
make net-allow        # определит подсеть сам и поставит правило
```

или вручную:

```bash
sudo ufw allow from 10.1.18.0/24 proto udp
sudo ufw reload
```

**Почему разрешается весь UDP, а не список портов.** Фиксированы только discovery-порты (для домена 42 это `7400 + 250×42 = 17900`). Весь остальной обмен FastDDS ведёт по **динамическим** портам, которые меняются при каждом перезапуске нод — правило по номерам портов будет работать до первого рестарта.

---

### ⚠️ Если сеть будет другой (выставка, другой роутер)

**Правило ufw привязано к подсети. В новой сети оно перестанет подходить, и симптом вернётся полностью — включая обманчиво живой ping.** Это первое, что нужно проверять на новой площадке.

Порядок действий на новом месте:

```bash
# 1. Посмотреть, что вообще происходит с сетью — sudo не нужен
make net-check

# 2. Открыть DDS для новой подсети (определится автоматически)
make net-allow

# 3. Прибраться: убрать правила от прежних сетей
bash mephi_hw_tests/ros2_net_setup.sh clean
```

`net-check` покажет интерфейс, SSID, IP, подсеть, состояние ufw и слушает ли DDS — этого достаточно, чтобы понять, где встало.

**Чек-лист для новой сети:**

- [ ] `ROS_DOMAIN_ID` одинаков на роботе и ноутбуке (у нас везде **42**)
- [ ] ufw открыт для **новой** подсети — `make net-allow`
- [ ] Старые правила убраны, чтобы не копились
- [ ] На ноутбуке `ros2 node list` показывает ноды робота
- [ ] Статический IP в `~/setup_network.sh` прописан под **старую** сеть `18KPU` (`10.1.18.175`). В другой сети Pi может не подняться вообще — проверьте до выезда

**Если ноды не появились даже после открытия ufw**, причина в multicast: многие точки доступа его режут (изоляция клиентов). Проверка:

```bash
# на роботе
ros2 multicast receive
# на ноутбуке
ros2 multicast send
```

Не дошло — переводите discovery на unicast. Создайте на **обеих** машинах файл `fastdds_peers.xml`:

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<dds xmlns="http://www.eprosima.com">
  <profiles>
    <participant profile_name="unicast" is_default_profile="true">
      <rtps>
        <builtin>
          <initialPeersList>
            <!-- Здесь адреса ВСЕХ машин: и робота, и ноутбуков -->
            <locator><udpv4><address>10.1.18.175</address></udpv4></locator>
            <locator><udpv4><address>10.1.18.69</address></udpv4></locator>
          </initialPeersList>
        </builtin>
      </rtps>
    </participant>
  </profiles>
</dds>
```

и подключите его перед запуском нод:

```bash
export FASTRTPS_DEFAULT_PROFILES_FILE=/полный/путь/fastdds_peers.xml
```

Адреса внутри файла придётся поправить под новую сеть — в этом и смысл: unicast не зависит от того, пропускает ли точка доступа multicast.

**Самый надёжный вариант для выставки — привезти свой роутер.** Тогда подсеть известна заранее, правило ufw ставится один раз, а поведение чужой точки доступа перестаёт вас касаться.

## 2. rviz ничего не показывает

**Симптом.** rviz2 запускается, но окно пустое. В левой панели красным: `Fixed Frame [map] does not exist`. Данные при этом идут — `ros2 topic hz /scan` подтверждает.

**Причина.** В `andino_bringup/rviz/andino.rviz` полем `Fixed Frame` был задан `map`. Этот фрейм публикуется **только при запущенном SLAM**. Без него у rviz нет системы координат, и он не рисует ни облако точек, ни модель робота.

Дерево TF без SLAM начинается с `odom`:

```
odom → base_link → second_base_link → rplidar_laser_link
```

**Лечение.** Исправлено коммитом `3bd50ee`: `Fixed Frame` переведён на `odom`, который публикует `diff_controller` всегда. У SLAM и Nav2 свои rviz-конфиги, их правка не затронула.

Если увидите это снова — переключите Fixed Frame на `odom` прямо в rviz (Global Options сверху слева) либо запустите SLAM.

## 3. В rviz нет модели робота

**Симптом.** Облако точек видно, робота нет. В логе десятки строк `Error retrieving file [package://andino_description/meshes/...]: Package [andino_description] does not exist`.

**Причина.** rviz на внешней машине получает URDF по теме `/robot_description`, но STL-меши в нём указаны как `package://` — их нужно взять с диска, а пакета на ноутбуке нет.

**Лечение.** Скопировать пакет на внешнюю машину и указать путь:

```bash
scp -r Vindicator2:/home/pi/MEPhi_SKIB_drone/MEPhI_ROS2_drone/install/andino_description ~/куда-нибудь/
export AMENT_PREFIX_PATH=~/куда-нибудь/andino_description:$AMENT_PREFIX_PATH
```

На ноутбуке это уже сделано: `~/Documents/vindicator/rviz.sh` поднимает rviz со всем необходимым.

## 4. Лидар отваливается по USB

**Симптом.** `/scan` перестаёт публиковаться. Нода `rplidar_composition` при этом **жива**, в логе ни одной ошибки.

**Причина.** Дребезг USB-контакта. Подтверждено практикой: помогает физическое передёргивание кабеля.

**Текущее лечение — костыль, но рабочий.** `mephi-lidar-watchdog.service` раз в 10 секунд проверяет `/scan`, при пропаже данных делает программный `usbreset` и перезапускает ноду. Восстановление занимает около 10 секунд.

Статистика на 22.08: **3 срабатывания**, последнее — при загрузке. После этого 2 ч 35 мин без сбоев.

**Что осталось.** Лечить причину: зафиксировать разъём механически, заменить кабель на короткий экранированный, проверить просадку питания. Watchdog оставить страховкой.

Лог: `/tmp/lidar_watchdog.log`

## 5. Радиус колеса расходится

**Не исправлено — нужен замер.**

Два файла задают радиус по-разному:

| Файл | Значение | На что влияет |
|---|---|---|
| `andino_description/config/andino/wheel.yaml` | `0.045` | модель в rviz |
| `andino_control/config/andino_controllers.yaml` | `0.035` | **одометрия** |

В контроллер загружено `0.035` (проверено через `ros2 param get /diff_controller wheel_radius`).

Разница **29 %**. Одометрия систематически врёт, карта SLAM плывёт, Nav2 промахивается.

**Что сделать.** Замерить колесо штангенциркулем, привести оба файла к реальному значению, пересобрать. Проверка — проехать размеченные 2 м и сверить с `/odom`.

Заодно не подтверждено `enc_ticks_per_rev: 585` — проверяется поворотом колеса ровно на один оборот со сверкой счётчика.

## 6. Нет часов реального времени

**Не исправлено — нужен модуль.**

`timedatectl` сообщает `RTC time: n/a`. При аптайме в 1 час система рапортовала о загрузке 26 августа 2025 — фиктивное время держалось, пока NTP не подтянул настоящее.

**Чем опасно.** Без интернета время останется неверным. Тогда TF-таймстампы уезжают, Nav2 отбрасывает «просроченные» данные, rviz показывает пустоту. Выглядит как полный отказ робота без единой ошибки в логе — то есть очень похоже на §1, и легко пойти искать не там.

**Лечение.** Модуль `DS3231` на I2C — полноценное решение, пока не поставлен.

**Сделано 22.08:** установлен `fake-hwclock` (enabled). Он сохраняет время при выключении
и восстанавливает при загрузке, так что откат на год назад больше не грозит. Точность он не
даёт — при длительном простое без сети часы всё равно отстанут, но скачок будет измеряться
часами, а не месяцами, и TF от этого уже не разваливается.

## 7. Три копии проекта на диске

| Путь | Что это |
|---|---|
| `~/MEPhi_SKIB_drone/MEPhI_ROS2_drone` | **рабочая.** Отсюда стартует systemd |
| `~/Documents/MEPhI_ROS2_drone` | версия коллеги, её прямой предок. В ней робот не ездил |
| `~/MEPhI_ROS2_drone_ws` | пустышка: симлинк на версию коллеги, `install/` не собран |

**Правьте только первую.** Проверить, откуда реально запущен робот:

```bash
systemctl cat mephi-bringup.service | grep ExecStart
```

Что было сломано в версии коллеги (починено 17 коммитами):

- `serial_device` мотора указывал на CP2102 — а это лидар, не мотор
- `baud_rate` 115200, хотя прошивка Arduino поддерживает только 57600
- включён временный режим «без энкодеров»
- инвертировано направление колёс
- переполнение счётчика энкодера (`unsigned int` вместо `int`)

## 8. Нет мультиплексора команд (twist_mux)

**Не исправлено — нужна установка.**

Конфиг `andino_bringup/config/twist_mux.yaml` с приоритетами в репозитории есть:

```
джойстик (30) → клавиатура (20) → навигация (10)
```

Но пакет **не установлен**, и в launch-файле не подключён.

**Чем опасно.** Джойстик и Nav2 пишут в `/cmd_vel` одновременно и перебивают друг друга. У оператора не будет способа перехватить управление, если робот поехал на посетителя. Ради этого приоритеты и задумывались.

**Лечение.**

**Сделано 22.08:** пакет установлен — `ros-humble-twist-mux 4.3.0` вместе с `twist-mux-msgs`.

**Осталось:** поднять ноду в bringup, развести источники по темам `cmd_vel_joy` и
`cmd_vel_keyboard`, а выход мультиплексора (`/cmd_vel_out`) завести на контроллер вместо
нынешнего прямого `/cmd_vel`. Правка затрагивает работающий стек и требует его перезапуска,
поэтому делается не на ходу.

```
Хост            pi@10.1.18.175 (Vindicator2), Raspberry Pi, Ubuntu 22.04.5
ROS             Humble, ROS_DOMAIN_ID=42
Wi-Fi           SSID 18KPU, статический IP задан в ~/setup_network.sh

Автозапуск      mephi-bringup.service, mephi-lidar-watchdog.service (оба enabled)

Порты
  Мотор (Arduino)  /dev/ttyUSB_MOTOR = /dev/ttyUSB_ARDUINO → CH340, 57600 бод

  udev-правила     udev/99-mephi-ros2-drone-usb-serial.rules

Нормальные показатели
  /odom   50 Гц

Прошивка МК       Arduino UNO, andino_firmware, текстовый протокол по UART
                  PID 30 Гц: Kp 10 · Kd 10 · Ki 0 · Ko 10
                  автостоп 3 с без команд
```

### Полезные команды

```bash
make net-check          # диагностика ROS 2 сети
make net-allow          # открыть DDS для текущей подсети
make ports              # какие USB-устройства видны и куда указывают симлинки
make udev-check         # на месте ли symlink'и портов
make bringup            # поднять робота руками (обычно уже поднят systemd)

journalctl -u mephi-bringup -f
tail -f /tmp/lidar_watchdog.log
```
